# Patched DNSChef For Mobile API Interception

This repository contains a patched DNSChef build for mobile API interception through Burp Suite.

The patch helps when a modern mobile device sends DNS `HTTPS` or `SVCB` queries before normal `A` queries. Older DNSChef code can fail on those record types or let the device continue using the real backend route instead of the Burp-routed address.

Use this only for systems you are authorized to test.

The examples use placeholder domains:

```text
api.example.test
example-alb-123456.eu-central-1.elb.amazonaws.com
```

Replace them with the in-scope API hostname and its CNAME/load balancer hostname.

## Setup

1. Clone or download this repository.

```sh
git clone https://github.com/everythingBlackkk/dnschef.git
cd dnschef
```

2. Create a Python virtual environment.

```sh
python3 -m venv .venv
```

3. Install dependencies.

```sh
./.venv/bin/pip install -r requirements.txt
```

4. Make the runner executable.

```sh
chmod +x ./dnschef-run
```

5. Find your Burp machine IP address on the same Wi-Fi network as the phone.

macOS example:

```sh
ipconfig getifaddr en0
```

Linux example:

```sh
ip -4 addr
```

In the examples below, the Burp/DNSChef machine IP is:

```text
192.168.1.3
```

6. Start patched DNSChef.

```sh
sudo ./dnschef-run \
  --fakeip 192.168.1.3 \
  --fakedomains api.example.test \
  --interface 0.0.0.0 \
  --logfile dnschef-api.log
```

Keep this terminal open while testing.

## Command Arguments

`--fakeip`

The IP address DNSChef should return for matching `A` queries. This should be the IP address of your Burp machine.

Example:

```sh
--fakeip 192.168.1.3
```

`--fakedomains`

Comma-separated domains that should resolve to `--fakeip`. Include the API hostname and its CNAME/load balancer hostname if one exists.

Example:

```sh
--fakedomains api.example.test
```

`--interface`

The network interface DNSChef listens on. Use `0.0.0.0` so the phone can reach DNSChef over Wi-Fi.

Example:

```sh
--interface 0.0.0.0
```

`--logfile`

Where DNSChef writes DNS activity logs.

Example:

```sh
--logfile dnschef-api.log
```

`--nameservers`

Optional upstream DNS server for domains not listed in `--fakedomains`. DNSChef defaults to `8.8.8.8`.

Example:

```sh
--nameservers 1.1.1.1
```

`--port`

Optional DNS listener port. Default is `53`. Port `53` normally requires `sudo`.

Example for local testing without sudo:

```sh
--port 5355
```

## Burp Setup

1. Open Burp Suite.
2. Go to `Settings -> Tools -> Proxy -> Proxy listeners`.
3. Add or edit a listener.
4. Set bind address to `All interfaces`.
5. Set bind port to `443`.
6. Enable `Support invisible proxying`.
7. Keep intercept off while testing, then turn it on when needed.
8. Install and trust Burp's CA certificate on the phone.

The important Burp listener state is:

```text
Bind address -> 0.0.0.0 / all interfaces
Bind port -> 443
Invisible proxying -> enabled
Certificate -> generated by Burp CA
```

If the app uses certificate pinning, trusting the Burp CA may not be enough. You need an authorized test build, a documented debug option, or an in-scope pinning bypass suitable for your assessment.

## Phone Setup

Use the same Wi-Fi network as the Burp/DNSChef machine.

1. Open Wi-Fi network settings.
2. Set DNS to manual.
3. Add only the Burp/DNSChef machine IP.
4. Turn HTTP proxy off.
5. Disable cellular data while testing, if the phone might bypass Wi-Fi.
6. Disable VPN, iCloud Private Relay, or similar traffic-routing features during testing.
7. Trust the Burp CA certificate.
8. Kill and reopen the mobile app after changing DNS.

Example phone settings:

```text
Wi-Fi DNS -> 192.168.1.3
HTTP proxy -> off
Cellular data -> off during test
VPN / Private Relay -> off during test
Burp CA -> trusted
```

## Patched Flow

```text
Mobile device DNS is set to 192.168.1.3
        ->
Mobile app starts HTTPS request to api.example.test
        ->
Mobile device asks DNSChef: api.example.test HTTPS
        ->
Patched DNSChef sees:
  qtype = HTTPS
  domain has a fake A record
        ->
Patched DNSChef returns an empty valid HTTPS response
        ->
Mobile device falls back to normal A lookup
        ->
Mobile device asks DNSChef: api.example.test A
        ->
Patched DNSChef answers: 192.168.1.3
        ->
Mobile app connects to 192.168.1.3:443
        ->
Burp invisible listener receives HTTPS traffic
```

## Why Original DNSChef Can Fail

Modern mobile operating systems may ask for these DNS records:

```text
A      -> IPv4 address
AAAA   -> IPv6 address
SVCB   -> service binding record, DNS type 64
HTTPS  -> HTTPS service binding record, DNS type 65
```

Original DNSChef uses this direct lookup:

```python
qtype = QTYPE[d.q.qtype]
```

Older `dnslib` versions do not know query type `65`. When a mobile device sends an `HTTPS` query, original DNSChef can throw:

```text
DNSError: QTYPE: Invalid forward lookup: [65]
```

Original failure flow:

```text
Mobile device asks DNSChef: api.example.test HTTPS
        ->
Original DNSChef tries: QTYPE[65]
        ->
Old dnslib does not know type 65
        ->
DNSError: QTYPE: Invalid forward lookup: [65]
        ->
DNSChef breaks or does not route cleanly
        ->
Traffic does not reliably reach Burp
```

## Patch Code Added

Add this helper near the DNSChef logger setup:

```python
def qtype_name(qtype):
    try:
        return QTYPE[qtype]
    except Exception:
        # Modern mobile clients commonly ask for SVCB/HTTPS records. Older
        # dnslib versions do not name them, but DNSChef can still handle them.
        return {
            64: "SVCB",
            65: "HTTPS",
        }.get(qtype, f"TYPE{qtype}")
```

This maps modern DNS query types safely:

```text
64 -> SVCB
65 -> HTTPS
unknown type -> TYPE<number>
```

## Patch Code Replaced

Replace the original direct lookup:

```python
qtype = QTYPE[d.q.qtype]
```

with:

```python
qtype = qtype_name(d.q.qtype)
```

This prevents DNSChef from crashing when it sees query type `64`, `65`, or another unknown type.

## Patch Code Added For HTTPS/SVCB Fallback

After DNSChef builds `fake_records`, add this block before the normal fake-record handling:

```python
if qtype in ("HTTPS", "SVCB") and fake_records.get("A"):
    log.info(f"{self.client_address[0]}: suppressing the response of type '{qtype}' for {qname} to force A fallback")
    response = DNSRecord(DNSHeader(id=d.header.id, bitmap=d.header.bitmap, qr=1, aa=1, ra=1), q=d.q)
    response = response.pack()
```

Then change the next fake-record check from:

```python
if qtype in fake_records and fake_records[qtype]:
```

to:

```python
elif qtype in fake_records and fake_records[qtype]:
```

This matters because DNSChef should not build a second response after it has already suppressed the `HTTPS` or `SVCB` response.

## What Was Deleted

No large block was deleted.

Only one original line was replaced:

```python
qtype = QTYPE[d.q.qtype]
```

The following `if` was changed to `elif`:

```python
if qtype in fake_records and fake_records[qtype]:
```
